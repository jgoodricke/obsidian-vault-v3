## Filter Questions

### Vacancy Mode Matching

The change affects three repository query paths, although the main live application path is `FacilityMapListRepository`, which serves both the map and potentially the facilities list. `VacancyMapListRepository` appears dormant but is still identified as an affected path.

The main technical complication is **vacancy-mode matching**. All selected services must exist on the **same vacancy**. For example, a facility with Service A on one vacancy and Service B on another must **not** match `[A, B]`. Therefore, the SSD constraints need to be grouped inside a single `whereHas('vacancies', ...)` query rather than independently checking each service across all of a facility's vacancies.

The intended implementation is to replace each existing `whereIn` match-ANY condition with **one `whereHas` constraint per selected SSD**. Room Type and Accommodation Type filters remain match-ANY and are explicitly out of scope.

# SSD Map Filter — Match-All Test Plan

Test matrix for changing the Map "Specific Service Deliveries" filter from match-ANY to match-ALL.

Each case deliberately isolates the SSD filter as the *cause* of exclusion (assert the facility matches on `[A]` alone, then stops matching on `[A, B]`) — this simultaneously proves narrowing and the "adding a service never increases results" acceptance criterion.

## `FacilityMapListRepositoryTest.php` (extend existing file)

| # | Mode | Setup | Assert |
|---|------|-------|--------|
| 1 | Facility | Facility has SSD A **and** B | matches `[A,B]` |
| 2 | Facility | Facility has **only** A | matches `[A]`; **not** `[A,B]` |
| 3 | Vacancy | One vacancy offers A **and** B | matches `[A,B]` |
| 4 | Vacancy | **Vacancy 1 offers A, Vacancy 2 offers B** (both live) | matches `[A]`; **not** `[A,B]` — the spread-across-vacancies guarantee |
| 5 | Vacancy | One vacancy offers **only** A | **not** `[A,B]` |
